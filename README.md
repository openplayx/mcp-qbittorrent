# mcp-qbittorrent

English | [简体中文](README.zh-CN.md)

[![License: GPL v3](https://img.shields.io/badge/license-GPLv3-blue.svg)](COPYING)

Server-side BitTorrent downloads for [OpenPlayX](https://github.com/openplayx/openplayx)
as an MCP server and HTTP API (formerly *bittorrent-server*): a restricted HTTP
API over a pinned **qbittorrent-nox 5.1.0** engine. The OpenPlayX App calls it through host-registered AI tools to add magnet /
`.torrent` downloads, follow progress, select files, pause, resume, limit and
remove tasks. Downloads run on the server and keep going when the App closes.

## What it is (and is not)

- Accepts only user-provided `magnet:` links and uploaded `.torrent` files.
  No search sites, indexers, remote torrent URLs (`xs`/`as`) or local paths.
- Every nested address (trackers, web seeds, peer hints) is checked against
  the network policy, not just the outer scheme. Disallowed ones (private,
  loopback — e.g. dead tracker domains now resolving to 127.0.0.1 — or
  unsupported schemes) are dropped and reported in `removed_addresses`; the
  rest of the magnet/torrent is used. `.torrent` files are rewritten without
  them (info dict untouched, so the info hash is unchanged). Only invalid
  inputs (no info hash, `xs`/`as` remote fetches) are rejected.
- Callers use logical `destination_ref`s and service task IDs. Engine
  credentials, SIDs, full magnets and absolute paths are never returned.
- Each torrent added through the API downloads into its own `opx-*`
  directory below its destination; removal keeps files unless a separately
  previewed plan says otherwise (the engine then deletes exactly that
  torrent's files).
- **Stateless**: the service stores nothing about tasks. Every read goes to
  the engine live; every torrent in the engine (including ones added in the
  WebUI) is listed and controllable, identified by its 40-hex engine hash.
  Plans and removal confirmations are signed tokens (per-process key, so
  they expire with a restart); uploaded `.torrent` files stay in memory for
  `input_ttl_seconds`. Selection/hold intent lives in engine tags
  (`opx-pending`, `opx-auto`, `opx-preset-video`, `opx-hold-*`). When the
  engine is down, reads answer `503 engine_unavailable`.

## Layout

```text
cmd/server/          API entry; also `new-token` and `engine-password-hash`
internal/api/        auth, rate limit, request/response, errors
internal/torrents/   stateless service: inputs, signed plans, live views, controls, tag automation
internal/qbittorrent qBittorrent 5.x WebUI API adapter (version-pinned)
internal/files/      authorised file references, symlink-safe reads/deletes
internal/webui/      guarded reverse proxy for the native WebUI
api/                 OpenAPI 3.1 (generated by scripts/gen-openapi.py) and /api/docs page
deploy/              Compose, API and engine images, config templates
scripts/             build, deploy, healthcheck, rollback, e2e
test/fakeqb/         in-process fake engine used by API tests
test/e2e/            Docker end-to-end suite against real qbittorrent-nox
docs/                operations, App integration
```

## Quick start

Requirements: Docker with Compose on the host; Go 1.26+ to build the binary.

```bash
go run ./cmd/server new-token my-client     # API token + its secrets.json entry
scripts/build.sh linux/amd64                # dist/bittorrent-server-linux-amd64 for the image
```

Then, in `deploy/`, create `.env` from `env.example`, `config/config.json` from
`config/config.example.json` and `config/secrets.json` from
`config/credentials.example.json`, and deploy with `scripts/deploy.sh`.
[docs/operations.md](docs/operations.md) walks through every step, the ports
and the engine's security settings. Check the result with
`curl -s http://<host>:<API_PORT>/api/readyz`.

Serve the API over HTTPS (built-in TLS or a reverse proxy) for anything beyond a
private LAN.

## Develop and test

```bash
go test -race ./...          # unit + API tests against the fake engine
scripts/e2e.sh               # real qbittorrent-nox in Docker (isolated network)
scripts/build.sh linux/amd64 # static binary in dist/
```

`scripts/e2e.sh` builds both images, generates throwaway credentials, starts
an isolated stack (the engine under test has no internet route; DHT/PeX/LSD
off), creates v1/v2/hybrid fixtures with a second engine acting as seeder and
tracker, and checks every acceptance item. It only
removes its own compose project and work directory.

## URL layout

One port serves both:

| Path | Served by |
|---|---|
| `/api/v1/…`, `/api/healthz`, `/api/readyz`, `/api/docs`, `/api/openapi.json` | this service (Bearer token) |
| everything else, incl. `/` and the WebUI's own `/api/v2/…` | qBittorrent's native WebUI through a guarded proxy (`webui.enabled`) |

Without the WebUI, `/` redirects to `/api/docs`.

## API at a glance

| Method & path | Purpose |
|---|---|
| `GET /api/healthz`, `GET /api/readyz` | liveness; database + engine readiness |
| `GET /api/v1/capabilities`, `GET /api/v1/destinations` | engine version, limits, destinations |
| `POST /api/v1/torrent-inputs` | upload a `.torrent` → short-lived `input_ref` |
| `POST /api/v1/torrent-plans` | validate magnet/input + destination → expiring plan |
| `POST /api/v1/torrents` | add from plan; 201 new, 200 if already in the engine |
| `GET /api/v1/torrents[/{id}]`, `GET /api/v1/torrents/{id}/files` | every engine torrent, live; files and selection revision |
| `PATCH /api/v1/torrents/{id}/selection` | change files against `files_revision` |
| `POST /api/v1/torrents/{id}/pause` / `resume` | confirmed against engine state |
| `PATCH /api/v1/torrents/{id}/limits` | per-task rates within admin ceilings |
| `POST /api/v1/torrents/{id}/remove-plan` / `remove` | preview, then apply |
| `GET\|HEAD /api/v1/torrents/{id}/files/{file_id}/content` | complete files, Range supported |

Full schema: `api/openapi.json`, rendered at `/api/docs`.

## MCP

`POST /api/mcp` exposes `list_destinations`, `create_plan`, `start_download`,
`list_downloads`, `get_download`, `pause`, `resume`, `create_remove_plan` and
`remove`. Downloads and removals stay two-step (plan, then execute with the
`plan_ref`); `.torrent` files are uploaded with `POST /api/v1/torrent-inputs`
and passed to `create_plan` as `input_ref`.

Streamable HTTP subset: single JSON-RPC 2.0 messages over `POST`, answered
with `application/json` (no SSE, no server-initiated messages); stateless (no
`Mcp-Session-Id`); `initialize`, `ping`, `tools/list`, `tools/call` and
notifications; protocol versions 2025-11-25, 2025-06-18 and 2025-03-26. The
same bearer token as the HTTP API is required on every request; requests with
a foreign `Origin` are refused. Business failures are tool results with
`isError: true` and the HTTP API's error codes. The MCP layer calls the same
service code as the HTTP handlers (no second state, no loopback request).

## WebUI

Users open the server root in a browser and log in with the engine's WebUI
account (`QBT_USERNAME` / engine password), not the API token. The proxy
(`internal/webui`):

- checks Origin/Referer against the browser-facing host, then rewrites
  Host/Origin/Referer so the engine's own Host and CSRF checks stay on;
- refuses global settings (`app/setPreferences`), shutdown, search plugins,
  RSS and the torrent creator — those buttons show an error in the UI;
- accepts only magnets and `.torrent` files for adds; save paths must stay
  inside the download root and outside the API's destination folders;
- limits failed logins per client IP (the engine's own ban is disabled,
  since every browser reaches it through the proxy's address).

WebUI and API act on the same engine: changes on either side show up on the other immediately.

## Using it from an MCP client

```json
{
  "mcpServers": {
    "qbittorrent": {
      "type": "http",
      "url": "https://bt.example.com/api/mcp",
      "headers": { "Authorization": "Bearer <token>" }
    }
  }
}
```

In OpenPlayX, the App's BitTorrent settings and AI tools use the HTTP API
directly; see [docs/app-integration.md](docs/app-integration.md).
